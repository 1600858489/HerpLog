## 开发原则

- 后端遵循 `Router → View → Schema → Service / Selector → Model`。
- 用户私有资源必须按 `user_id` 隔离；跨用户访问统一表现为 NotFound。
- 请求体继承 `BaseRequestSchema`，拒绝内部字段；API 仅返回 UUID，不返回内部自增 ID。
- Selector 保持只读并明确预加载关系；Service 负责写入、业务状态转换和原子操作。
- 每个新增业务域必须独立建模、独立测试；不要把 Event、State 或 Care Plan 塞入宠物档案模块。
- 先写失败测试，再写最小实现；每个里程碑完成前运行全量后端测试、编译检查、OpenAPI 检查和前端相关测试。

## 后续里程碑

### M1：前端接入宠物档案 API

**目标：** 用后端持久化数据替换宠物、分类和管理单元相关 Mock 数据。

**范围：**

- 建立前端 HTTP 客户端、认证令牌存储、刷新令牌流程和统一错误映射。
- 将宠物列表、宠物详情、物种、基因、标签、管理单元和成长/来源记录替换为真实 API 调用。
- 为表单和列表实现加载、空态、提交失败和 401 登录失效处理。
- 保留 Event、Today、Timeline、Dashboard 的 Mock 数据，直到 M2-M3 有对应后端 API。

**完成条件：**

- 刷新页面后，宠物档案数据仍来自后端数据库；不再从 `frontend/src/mocks/repository.ts` 读取宠物数据。
- 用户 A 不能在 UI 或 API 中查看用户 B 的宠物数据。
- 前端 typecheck、测试、生产构建通过；后端全量测试仍通过。

### M2：事件域与 Timeline

**目标：** 为实际饲养记录提供持久化 Event 数据，并让 Timeline 使用真实事件查询。

**范围：**

- 新建独立 `events` 业务包，包含模型、Schema、Selector、Service、View 与测试。
- 首批事件类型：喂食、体重、排泄、蜕皮、用药、环境和自定义记录。
- 每条事件绑定用户与宠物，记录发生时间、类型、结构化负载、备注和软删除状态。
- 提供宠物维度和用户全局维度的分页 Timeline 查询；按发生时间稳定倒序。
- 前端 Record 创建真实事件，Timeline 渲染真实查询结果。

**完成条件：**

- 所有事件 API 均经过用户隔离、输入验证和软删除测试。
- Timeline 刷新后不丢失记录，且能按宠物筛选、分页与稳定排序。
- 宠物删除对事件历史的处理规则被明确建模并通过测试验证。

### M3：状态与护理计划

**目标：** 基于宠物档案和事件记录推导宠物当前状态、护理规则与 Today 待办。

**范围：**

- 新建独立 `care` 或 `plans` 业务包，管理饲养规则、间隔、暂停条件和适用宠物。
- 定义状态来源：哪些状态由用户直接维护，哪些由事件与规则推导；禁止在 View 中拼接业务规则。
- 提供 Today 查询：待办、逾期、暂停原因和下一次建议时间。
- 支持前端现有的喂食、称重规则，且冬化等暂停状态必须能阻止不适用的待办。

**完成条件：**

- 同一输入事件和规则始终导出相同的待办结果；规则推导有纯 Service/Selector 测试。
- Today 与 Dashboard 不再依赖 Mock `derive.ts` 作为生产数据来源。
- 时间边界、时区、暂停和过期条件都有 API 与业务层测试。

## 推荐执行顺序

1. M1 的前端 HTTP 客户端与认证流程。
2. M1 的宠物、分类资料与管理单元页面接入。
3. M2 的 Event 数据模型、写入 API 与 Timeline 查询。
4. M2 的 Record、Timeline 前端接入。
5. M3 的护理规则与 Today 推导。
6. M4 的迁移、配置和部署验证。

每个里程碑开始前，另建一份针对该里程碑的实施计划；不要直接依据本路线图编写跨域代码。
